Kerjakan user testing

Uji penggunaan nyata dan catat hasil aktual dari orang yang menjalankan program.

BAYANGKAN BEGINI

Seperti meminta pelanggan mencoba meja kasir sebelum digunakan rutin.

Coba sekarang: Buat satu kasus normal dan satu kasus input salah.
Konteks Akademik (Dokumen Before Sidang): Dokumen User Testing (UT) adalah dokumen pra-sidang (Before Sidang). Mahasiswa wajib menguji program secara empiris kepada pengguna/kasir, mencatat hasil aktual, dan melampirkan rekaman screenshot sebelum melangkah ke meja sidang penguji.
BEDAH ANATOMI Fig 2.1 · Anatomi Matriks User Testing (UT) — Dokumen Before Sidang

Anatomi 6 Komponen Baris Dokumen Pengujian (Before Sidang)

Tahap 1 / 3
1 ID Kasus (TC-XX): Pengenal unik baku untuk setiap baris uji agar mudah dirujuk saat revisi sidang.
2 Kasus Normal vs Negatif: Wajib memadukan uji jalan mulus (Happy Path) dan uji serangan input salah (Boundary/Negative).
3 Expected vs Actual: Expected ditentukan dari spesifikasi awal; Actual ditulis murni dari kejadian nyata di console.
4 Status & Defect: Status FAIL bukanlah kegagalan mahasiswa, melainkan penemuan defect yang sah untuk dicatat dan diperbaiki.
Kaidah Before Sidang: Dosen penguji memeriksa dokumen User Testing ini saat sidang untuk membuktikan integritas pengujian pra-sidang. Penguji sangat menghargai tabel testing yang mencatat kegagalan nyata (defect) dan bukti perbaikannya, daripada tabel yang dipaksakan Lulus (PASS) palsu.

User Testing (UT) Bug Hunter Simulator

Praktikkan langsung 18 skenario pengujian Dokumen User Testing (UT). Bobol form dengan kasus negatif terlebih dahulu untuk membuka akses data valid!

Buka Simulator Pengujian

Kapan dikerjakan? Siapkan kasus uji dan kerangka dokumen sekarang. Setelah latihan program tersedia, kembali ke modul ini untuk menjalankan uji, mengisi hasil aktual, dan mengambil screenshot. Nomor modul mengelompokkan materi; hasil testing mengikuti waktu pelaksanaan.

Identifikasi penguji dan lingkungan, siapkan data awal, tuliskan langkah serta ekspektasi, lalu jalankan program. Isi hasil test, tester, tanggal, bukti, dan keterangan sesuai kejadian. Jika gagal, tulis defect dan uji ulang setelah perbaikan.

Kasus Langkah Ekspektasi Hasil Aktual
Normal Beli 2 buku @12.000, bayar 30.000 Total 24.000, kembali 6.000 Belum diuji
Input salah Masukkan qty huruf atau negatif Ditolak, pesan jelas, data tidak berubah Belum diuji
Simpan gagal Coba saat file tidak dapat ditulis Tidak menyatakan sukses atau membuat nota baru Belum diuji
Peringatan Kejujuran Sidang: Jangan mengisi Diterima atau Lulus sebelum percobaan benar-benar dijalankan. Contoh PDF merupakan referensi format, bukan bukti KasirKita telah lulus.
Kasus Kondisi Awal Pemeriksaan Sesudah Uji
Normal Produk P001: stok 20, harga 12.000; jumlah 2, bayar 30.000 Target: stok 18; SALE dan ITEM cocok dengan nota, kembali 6.000
Input salah Catat isi record dan stok sebelum uji Target: record dan stok tidak berubah
Simpan gagal Gunakan salinan data latihan; catat record/stok, lalu buat lokasi simpan tidak dapat ditulis Target: tidak ada nota sukses atau penyimpanan sebagian; bandingkan SALE, ITEM, dan stok, catat kegagalan aktual

Kasus checkout adalah rancangan uji untuk program yang dibuat bersama pengajar. Latihan satu file C pada modul 3–4 belum mengimplementasikan checkout. Jika fiturnya belum tersedia, tulis Belum dapat diuji beserta alasannya. Pulihkan izin/lokasi file setelah uji pada data salinan.

BEDAH ANATOMI Fig 2.3 · Anatomi Product Documentation & Arsitektur Standalone C

Anatomi Arsitektur Standalone C & Relasi Persistensi File TXT

Tahap 1 / 3
1 Arsitektur Standalone: Program berjalan native di console Windows tanpa memerlukan server web atau DBMS eksternal yang rumit.
2 Persistensi File TXT: Seluruh data disimpan persisten dalam file teks menggunakan fungsi I/O C baku (fopen, fgets, fprintf).
3 Modular Library (lib.h): Header pendukung yang merangkum fungsi API Windows untuk posisi kursor, border kotak, dan input aman.
4 Error Guarding Mutlak: Pemeriksaan file == NULL wajib dicatat di SRS & kode C demi mencegah crash tak terduga di depan penguji.
Panduan SRS Sidang: Jika template dokumen menyebut API/DBMS, jelaskan secara jujur bahwa KasirKita memakai arsitektur C Standalone & TXT File Processing.
